# Low-Level Design (LLD)
## StudentHub

**Document version:** 1.0
**Last updated:** 2026-08-14

## 1. Purpose

This document details the concrete data model, API contract, and per-endpoint behavior implemented in the current codebase (`server/prisma/schema.prisma`, `server/src/routes/*`, `server/src/controllers/*`). It complements the HLD (component/architecture view) and the PRD (requirements/scope view).

## 2. Data Model (Prisma / MongoDB)

All primary keys are MongoDB ObjectIds (`@id @default(auto()) @map("_id") @db.ObjectId`).

### 2.1 `User`
| Field | Type | Notes |
|---|---|---|
| id | ObjectId | PK |
| name | String | required |
| username | String | **unique** |
| email | String | **unique** |
| password | String | bcrypt hash |
| role | Role? | STUDENT \| TEACHER, nullable until chosen |
| bio, avatar, phone | String? | optional profile fields |
| teachingTopics | String[] | default `[]`; editable independent of any specific course |
| createdAt / updatedAt | DateTime | auto |
| Relations | — | coursesTaught, enrollments, progress, reviews, quizzes, quizAttempts, rewards, notifications, learningActivity |

### 2.2 `Course`
| Field | Type | Notes |
|---|---|---|
| id | ObjectId | PK |
| title | String | required |
| description | String? | optional |
| link | String | required — the external resource URL |
| category | String | required (e.g. Web Dev, Programming, Data Science, AI & ML) |
| difficulty | Difficulty | default BEGINNER |
| thumbnail | String? | optional |
| teacherId | ObjectId | FK → User, `onDelete: Cascade` |
| views | Int | default 0, incremented on detail view |
| createdAt / updatedAt | DateTime | auto |
| Relations | — | enrollments, reviews, progress, lessons (`CourseLesson`), quizzes, views_log (`CourseView`) |

### 2.3 `Enrollment`
`studentId` + `courseId` FKs (cascade delete). `bookmarked: Boolean` (default false). `enrolledAt: DateTime`.
**Unique constraint:** `[studentId, courseId]` — a student can only have one enrollment record per course (enrollment and bookmark state share this row).

### 2.4 `Progress`
`studentId` + `courseId` FKs (cascade delete).
- `completionPercentage: Int` (default 0)
- `lessonsCompleted: Int` (default 0)
- `completedLessonIds: String` (default `"[]"`, JSON-encoded array of lesson IDs)
- `lastAccessedAt: DateTime` (`@updatedAt`)
**Unique constraint:** `[studentId, courseId]`.

### 2.5 `Review`
`rating: Int` (1–5), `comment: String?`. `studentId` + `courseId` FKs (cascade delete).
**Unique constraint:** `[studentId, courseId]` — one review per student per course (enforced at the schema level; `updateReview`/`deleteReview` mutate the existing row rather than creating a new one).

### 2.6 `CourseLesson`
Belongs to a `Course` (cascade delete). `order: Int`, `title: String`, `videoUrl: String?`, `duration: String?`. Populated by the course-ingestion pipeline (see HLD §4) or manually.

### 2.7 `CourseView`
Belongs to a `Course` (cascade delete). `userId: String` (not a relation FK to User — stored as a raw ObjectId string, allowing anonymous/optional-auth views to still be attributable if a user id is present). `viewedAt: DateTime`.
**Unique constraint:** `[userId, courseId]` — a given user is only counted once per course for the purpose of duplicate-view prevention.

### 2.8 `Quiz`
`title`, `description?`. `creatorId` FK → User (cascade delete). `courseId` FK → Course, **optional** (a quiz may be standalone or tied to a course). `autoGenerated: Boolean` (default false). `questions: String`, `answers: String` — both JSON-encoded arrays stored as strings (not native arrays, to accommodate variable question schemas). Relation: `attempts` (`QuizAttempt[]`).

### 2.9 `QuizAttempt`
`userId` + `quizId` FKs (cascade delete). `score: Int`, `totalQuestions: Int`, `percentage: Float`. `createdAt: DateTime`. Used to compute leaderboards.

### 2.10 `LearningActivity`
`userId` FK (cascade delete). `date: String` (day-granularity identifier). `createdAt: DateTime`.
**Unique constraint:** `[userId, date]` — at most one activity record per user per day; `utils/streak.js` derives a consecutive-day streak from these rows.

### 2.11 `Reward`
`userId` FK (cascade delete). `type: RewardType` (BADGE \| COUPON \| POINTS). `badge?`, `coupon?`, `points: Int` (default 0). `earnedAt: DateTime`.

### 2.12 `SponsoredCoupon`
`sponsor: String` (e.g. "Skillshare", "JetBrains"), `code: String`, `description?`. `claimed: Boolean` (default false), `claimedByUserId: String?` (raw id, not a relation), `claimedAt: DateTime?`. No FK relation to `User` — claim is tracked by id string only.

### 2.13 `Notification`
`userId` FK (cascade delete). `message: String`, `type: NotificationType` (ENROLLMENT \| REVIEW \| COURSE_PUBLISHED \| ACHIEVEMENT), `read: Boolean` (default false). `createdAt: DateTime`.

### 2.14 Enums
```
Role:              STUDENT | TEACHER
Difficulty:        BEGINNER | INTERMEDIATE | ADVANCED
RewardType:        BADGE | COUPON | POINTS
NotificationType:  ENROLLMENT | REVIEW | COURSE_PUBLISHED | ACHIEVEMENT
```

### 2.15 Entity Relationship Summary
```
User 1───* Course        (teacherId)
User 1───* Enrollment    (studentId)   Course 1───* Enrollment (courseId)
User 1───* Progress      (studentId)   Course 1───* Progress   (courseId)
User 1───* Review        (studentId)   Course 1───* Review     (courseId)
Course 1─* CourseLesson
Course 1─* CourseView            User(id, unattached) referenced by userId
User 1─* Quiz (creatorId)        Course 0..1─* Quiz (courseId, optional)
User 1─* QuizAttempt             Quiz 1─* QuizAttempt
User 1─* LearningActivity
User 1─* Reward
User 1─* Notification
SponsoredCoupon  (standalone; claimedByUserId is an unenforced reference)
```

## 3. API Reference

Base path: `/api`. All request/response bodies are JSON. Protected endpoints require header `Authorization: Bearer <jwt>`; `authMiddleware` returns `401 { msg: "No token" }` or `401 { msg: "Invalid token" }` on failure. Endpoints marked "optional auth" use `optionalAuth` — they never reject for a missing token, but personalize the response if a valid one is supplied.

### 3.1 Health
| Method | Path | Auth | Description |
|---|---|---|---|
| GET | `/api/health` | none | Returns `{ status: "ok"|"degraded", timestamp, integrations }`. `degraded` when a required env var is missing. |

### 3.2 Auth (`authRoutes.js` → `authControllers.js`)
| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/api/auth/signup` | none | Body: `{ name, username, email, password }`. Hashes password (bcrypt), creates `User`, returns token + user. Rejects duplicate email/username. |
| POST | `/api/auth/login` | none | Body: `{ email, password }`. Verifies hash, issues JWT (7-day expiry). |

### 3.3 User (`userRoutes.js` → `userController.js`)

| PATCH | `/api/user/email` | required | Changes email (with validation for uniqueness). |

## 4. Middleware Detail

### 4.1 `authMiddleware.js` (required auth)
```
token = req.headers.authorization?.split(" ")[1]
if !token → 401 { msg: "No token" }
try: decoded = jwt.verify(token, process.env.JWT_SECRET); req.user = decoded; next()
catch → 401 { msg: "Invalid token" }
```

### 4.2 `optionalAuth.js`
```
token = req.headers.authorization?.split(" ")[1]
if !token → next()  // proceed unauthenticated
try: req.user = jwt.verify(token, process.env.JWT_SECRET)
catch → swallow error, proceed unauthenticated
next()
```

### 4.3 `errorHandler.js` (terminal middleware)
```
statusCode = err.statusCode || 500
message = err.message || "Internal server error"
respond { msg: NODE_ENV === "production" ? "Something went wrong" : message }
```
Controllers that want a specific status code throw/pass an `Error` with a `.statusCode` property (e.g., 400 for validation, 403 for ownership violations, 404 for not found).

## 5. Server Bootstrap Detail (`index.js`)

1. Load `.env` via `dotenv`.
2. Instantiate Express app; apply `cors()` and `express.json()` globally.
3. Register `GET /api/health` before other routes.
4. Mount all ten resource routers under their `/api/<resource>` prefixes (see §3).
5. Mount `errorHandler` last (must be last for Express to treat it as an error handler).
6. `startServer(port, retriesLeft = 10)`:
   - Attempts `app.listen(port)`.
   - On `EADDRINUSE`, if the port was not explicitly pinned via `process.env.PORT`, retries on `port + 1`, decrementing `retriesLeft`, until exhausted.
   - Any other bind error, or retries exhausted, logs and calls `process.exit(1)`.
7. `initialPort = Number(process.env.PORT) || 5000`.

## 6. Course Ingestion Pipeline — Function-Level Detail

`services/courseAnalyzer.js :: analyzeCourseLink({ title, description, category, link })`

1. `parseYouTubeUrl(link)` → `{ type: "playlist"|"video"|null, playlistId?, videoId? }`.
2. If `type === "playlist"` and `playlistId`: `fetchYouTubePlaylist(playlistId)` → lessons; `source = "youtube_api"` if non-empty.
3. Else if `type === "video"` and `videoId` and no lessons yet: `fetchYouTubeVideo(videoId)` → single-lesson array; `source = "youtube_api"`.
4. If still no lessons and `process.env.OPENAI_API_KEY` set: `generateLessonsWithAI({ title, description, category, link, parsed })`; `source = "openai_curriculum"`.
5. If still no lessons: `fallbackLessons({ title, link, parsed })`; `source = "playlist_heuristic"` or `"link_heuristic"` depending on `parsed.type`.
6. If it's a single video with exactly one lesson: attach `videoUrl = buildVideoUrl(videoId, playlistId)`.
7. If `OPENAI_API_KEY` set: `refineLessonTitles({ title, description, lessons })` rewrites titles; append `"+ai_titles"` to `source`.
8. Default quiz: `fallbackQuiz({ title, lessons })`.
9. If `OPENAI_API_KEY` set: overwrite with `generateCurriculumAndQuiz({ title, description, category, link, lessons })`; append `"+ai_quiz"` to `source`.
10. Return `{ lessons, quiz, source, parsed }` to the caller (`courseController.addCourse`), which persists `CourseLesson` rows and an auto-generated `Quiz` (`autoGenerated: true`) linked to the new course.

This function is pure orchestration — it has no direct Prisma/DB calls; persistence happens in the calling controller.

## 7. Validation & Error Conventions

- Duplicate email/username on signup → rejected with a client error (Prisma unique-constraint violation caught and translated to a 4xx `msg`).
- Duplicate review/enrollment/progress/course-view for the same (user, resource) pair → prevented by Prisma `@@unique` constraints; controllers should catch the constraint violation and respond with a conflict rather than a 500 (verify per-controller when modifying this area — no centralized conflict-mapping middleware exists today).
- Ownership violations (editing/deleting another user's course/quiz/review) → controller-level checks comparing `req.user.id` to the resource's owner field, before mutating.
- All uncaught errors funnel to `errorHandler.js` and are logged server-side (`console.error("ERROR:", err)`), with sanitized messages returned to the client in production.

## 8. Known Implementation Gaps (for future LLD revisions)

- No request-body schema validation library (e.g., Zod/Joi) is wired in yet — controllers validate manually/partially.
- No rate limiting middleware.
- No automated test suite backing these contracts — this LLD is derived from static code reading, not from executed integration tests.
- `SponsoredCoupon.claimedByUserId` and `CourseView.userId` are stored as raw strings rather than Prisma relation fields, so referential integrity for these two links is not enforced by the database.
